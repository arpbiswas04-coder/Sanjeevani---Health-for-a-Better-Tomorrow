# Mutual-TLS federation transport

The new private-development HTTPS service connects signed update admission to
regional clients. It uses the existing FedAvg coordinator and checkpoint format.
The client command trains through the existing Flower/PyTorch adapter, then sends
only the signed update. This is a custom HTTPS protocol, not Flower's network runtime.

## Credentials

For localhost demonstrations, use the [local provisioning and launch helper](federated-local-setup.md).
It creates short-lived credentials and injects the environment variables described
below. The remaining instructions also support separately provisioned credentials.

Provision certificates using your private CA and keys through your secret manager:

- Server: a certificate with serverAuth extended key usage and a DNS/IP subject
  alternative name matching the client URL, plus its private key.
- Each node: a separate clientAuth certificate and private key. Its SAN must have
  exactly one federation identity URI, for example
  `urn:sanjeevani:node:district-a`. The node must exist in the coordinator registry.
- Server trust bundle: the CA issuing the node certificates. Client trust bundle:
  the CA issuing the server certificate. They may be different CAs.
- Each node: its own independent random HMAC key (at least 32 bytes). The server
  receives the complete node-to-key mapping. Do not share other nodes' keys.

The server reads `SANJEEVANI_NODE_KEYS_JSON`, a JSON object mapping registered node
IDs to hex-encoded HMAC keys. Each client reads only `SANJEEVANI_NODE_KEY_HEX`.
Inject these environment variables through your launcher; do not paste secrets
into commands, logs or tracked files. New state uses the three nodes in
`federated/configs/demo.json`; restored state uses its saved registry.

Paths below assume provisioned PEM files under ignored `federated/secrets/`.
Git ignoring is not access control: restrict that directory to the service user.
No persistent certificates or credentials were generated by this implementation.
Encrypted private-key files and interactive passphrases are not an unattended
deployment mechanism; use restricted service-readable key files for this prototype.

## Run

From `infra/`, after injecting the server environment variable:

```powershell
.\.venv-federated\Scripts\python.exe -m federated.server.https --ca federated/secrets/node-ca.pem --cert federated/secrets/server.pem --key federated/secrets/server.key --checkpoint federated/checkpoints/https.json --round-seconds 120
```

The default listener is `127.0.0.1:8443`. The server requires mutual TLS for all
requests. It validates the client certificate chain and binds the certificate's
URI node identity to the signed update's node identity. There is no plaintext mode.

In each node's process, inject only its HMAC environment variable and run once per
round (replace the district and credential paths for nodes b and c):

```powershell
.\.venv-federated\Scripts\python.exe -m federated.clients.https --url https://localhost:8443 --node district-a --ca federated/secrets/server-ca.pem --cert federated/secrets/district-a.pem --key federated/secrets/district-a.key
```

The client validates the server CA and URL hostname. It fetches the round,
trains synthetic local data using PyTorch, signs the update and submits it. It
does not follow redirects, bypass verification or retry automatically. A lost
acknowledgement may mean an update is already pending; duplicate submissions are
rejected. Start clients early enough to train before the deadline. No polling,
automatic client scheduler or global-model evaluation endpoint is provided yet.

## Endpoints and rounds

| Endpoint | Access | Result |
| --- | --- | --- |
| `GET /v1/round` | Registered client certificate | Model parameters, schema/version, round and challenge |
| `POST /v1/updates` | Registered certificate plus matching HMAC identity | HTTP 202 when pending; generic rejection otherwise |

Updates require exactly one Content-Length, no Transfer-Encoding, a JSON content
type and a body at most 16 KiB. Connections close after each response; bodies and
credentials are not logged. There is no participant-accessible close-round or
administration endpoint.

The server closes a round every configured interval (10–3600 seconds), even when
too few clients participated. At least two valid updates are required for a new
model. Each closed round is checkpointed; a persistence error stops the service.
An existing checkpoint is validated and restored at startup. Ctrl+C discards
pending updates; clients must fetch a fresh challenge after restart. Do not run
multiple service instances against the same checkpoint.

## Scope and validation

This is a sequential private-development server, not an internet-facing
production deployment. Five-second socket inactivity timeouts bound individual
stalls but do not provide absolute request deadlines; slow requests can delay
round closing. Rate limiting, robust concurrency, certificate revocation/rotation,
secret-manager integration and deployment monitoring remain pending. HMAC and TLS
do not prevent poisoning by an authorized node or provide differential privacy.

The implementation follows Python's [TLS certificate verification APIs](https://docs.python.org/3/library/ssl.html).
Python's [HTTP server documentation](https://docs.python.org/3/library/http.server.html)
also describes the limitations of this development server foundation.

The focused integration test creates short-lived certificates in a temporary
directory, starts a localhost listener on an ephemeral port, checks mutual TLS,
hostname verification, unregistered/cross-node identities, signatures, replay,
body limits and aggregation, then closes the listener and removes the fixtures.
It does not train models. Fixture generation uses `cryptography`, already present
in the separate federation environment; the service itself uses the standard library.

```powershell
.\.venv-federated\Scripts\python.exe -m unittest federated.tests.test_https federated.tests.test_admission -v
```
